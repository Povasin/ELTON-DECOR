# Развёртывание и эксплуатация

Статус: **предложенный план**, 2026-10-06. Облачные проекты, серверы, БД, storage, домены, сертификаты, секреты, CI и окружения не созданы. Ничего не развёрнуто. Выбор плагинов разрешает подготовку; он не означает разрешения купить услуги, передать личные данные или публиковать production.

## Предложенная схема размещения

Базовый кандидат — согласованный регион: контейнеры FastAPI API и Celery worker/beat, PostgreSQL, Redis для очередей/временных ограничений, S3-совместимое private storage фото возвратов. Storefront и admin — два Next.js/TypeScript приложения в monorepo; размещение на совместимом frontend hosting либо в том же региональном контуре требует решения. PostgreSQL — источник локальных заказов и финансового ledger, Redis его не заменяет.

| Компонент | Предложенная роль | Условие выбора / состояние |
| --- | --- | --- |
| Региональные контейнеры | API, worker и beat; изолированные runtime-секреты | Поставщик, регион, ресурсы и роли не выбраны |
| PostgreSQL | Заказы, снимки цен, резервы, платежи/возвраты, inbox/outbox | Backup/PITR и restore drill обязательны; БД не создана |
| Redis | Фоновые задачи, временные ключи/лимиты | Восстановление операций из БД проектируется; ресурс не создан |
| S3-совместимый private storage | Фото возвратов, серверная авторизация, кратковременные ссылки | Регион, retention, шифрование и backup не выбраны |
| Vercel, опционально | Preview/hosting storefront и admin | Кандидат; проверить путь данных, логов, CDN и preview до production |
| Supabase, опционально | Управляемые PostgreSQL и Storage | Кандидат; регион/размещение данных не решены. Не автоматическая замена SMS/admin auth |

При выборе Supabase PostgreSQL **Alembic остаётся единственным владельцем прикладной схемы**. Python-модели/миграции — в `packages/database`; папка не означает npm-пакет. Ручные schema edits через dashboard, отдельные Supabase migrations или другой ORM не создают вторую миграционную систему. Служебные схемы провайдера отделяются от прикладной; права фиксируются до provisioning.

Открыты допустимые регионы и размещение PII, media, backups, очередей, логов и доступа поддержки, включая трансграничные потоки frontend/CDN/SMS/Ozon. Решение принимается до реальных данных. Региональное размещение базового кандидата само по себе не доказывает выполнение всех требований.

## Окружения и зависимости

- Local: синтетические данные/mock; без production-ключей и настоящих SMS/платежей по умолчанию.
- Preview: защита доступа, синтетические данные, изоляция ресурсов; нет подключения к production-БД/media. Fork PR не получает секреты.
- Staging: отдельные БД, Redis, storage, credentials и hostname; только подтверждённый sandbox. Его отсутствие фиксируется в gate, а не маскируется mock.
- Production: после согласования архитектуры/данных, готовности интеграций и разрешения выпуска.

Frontend вызывает API; бизнес-правила и права исполняет API. Worker/beat — отдельные runtime-процессы с entrypoints в `apps/api`; они используют те же доменные правила, схему и проверенный adapter. Beat требует единственного активного планировщика либо доказанной защиты от дубликатов; идемпотентность обязательна при любом числе экземпляров. Реплики и ресурсы определяются измерениями и пока не заданы.

## Предложенные будущие GitHub Actions gates

Workflow-файлы и настройки репозитория здесь **не созданы**. После утверждения предлагается реализовать:

1. Формат/линтеры/типы TypeScript/Python и domain tests; secret scan и проверка зависимостей по согласованной политике.
2. PostgreSQL integration tests: concurrent reservations, ledger, inbox/outbox, retries и unknown payment/refund; frontend/API contracts и schema analytics.
3. Воспроизводимые сборки storefront, admin и выбранных Python runtime-артефактов; API и worker могут использовать один образ с разными entrypoints. Артефакт связан с commit, зависимостями и миграциями; секреты исключены из build output/client variables.
4. Alembic: пустая и предыдущая схема, совместимость старого/нового кода при rollout, review опасных изменений; одна отдельная задача миграций, а не запуск каждым API/worker.
5. Provider contract tests в защищённом контуре с тестовыми credentials, без секретов для fork PR. Seller API fixture не подтверждает внешний checkout.
6. Staging E2E, permissions/private media и restore drill БД/media. Production gate получает доказательства и явное разрешение выпуска.

Проверки PR без секретов отделены от защищённых jobs. Branch protection, минимальные permissions, политика сторонних Actions/runner и approvals — будущие настройки. Ни один зелёный gate не заявлен; критерии QA-G0…QA-G6 и доказательства приёмки в [QA.md](QA.md).

## Предложенный порядок выпуска

1. Зафиксировать согласованные артефакты/release/config и оценку миграций; проверить backup/restore.
2. Одной контролируемой задачей применить обратно совместимые расширяющие миграции. Старые API/worker работают до смены экземпляров; разрушительные изменения — отдельный выпуск после окна совместимости.
3. Развернуть API/worker по порядку контрактов, безопасно завершить/повторить задачи; frontend после готовности API.
4. Smoke без реального списания: каталог, guest cart, auth, protected endpoints, очередь/callbacks по безопасной процедуре; проверить ошибки, лаги и unknown.
5. При нарушении gate остановить продвижение, вернуть совместимые приложения к предыдущим артефактам. Схема и финансовые операции не откатываются механически вместе с кодом.

Откат схемы требует оценки сохранности данных; предпочтительны совместимость и исправляющая миграция. Backup/PITR — процедура аварии с согласованной точкой времени. После восстановления обязательна сверка с провайдером: внешний платёж/refund может существовать после восстановленной точки БД. Повторная отправка всех задач без сверки недопустима.

## Backup и restore

До production согласовать RPO/RTO и проверить измерением. Кандидат — регулярный backup PostgreSQL/PITR при доступности, независимая проверка восстановления, защищённые копии media и политики версий/удаления. Период, retention, стоимость и регион копий открыты.

Restore drill: восстановить в изолированном окружении; проверить количество/связность заказов, ledger, возвратов, private media и права; отключить исходящую отправку платежей/SMS; сверить пропущенные события и выполнить safe replay inbox/outbox. Записать длительность, точку восстановления, потерю данных и расхождения. Файл backup не доказывает восстановление.

## Наблюдаемость

Структурированные логи: correlation ID, локальные order/payment/refund ID, проверенные внешние ID, channel, переход/ошибка, release. Запрещены секреты, SMS-коды, cookie, реквизиты, полный телефон/адрес, фото и сырые provider payload. Redaction проверяется тестом; политика в [SECURITY.md](SECURITY.md).

| Сигнал | Назначение | Предлагаемая реакция |
| --- | --- | --- |
| Возраст/число unknown payments/refunds; ledger/provider mismatch | Найти незавершённые финансовые операции | Сверка; ограничение конфликтующих операций; без слепого retry |
| Последний stock sync, возраст stale/failed SKU | Найти недостоверную доступность | Согласованная stale policy, проверка провайдера |
| Inbox/outbox backlog/возраст, retries/dead-letter | Найти задержку и неисправные события | Проверка worker/adapter, обезличенная диагностика, safe replay |
| Callback signature failure/unknown ID/duplicate/out-of-order | Найти нарушения контракта или атаки | Проверка подлинности/связи; непроверенные события не меняют состояние |
| API latency/error, DB connections/locks, queue/task duration | Доступность и узкие места | Устранение причины; масштабирование после измерения |
| SMS/admin auth errors, rate limits, отказы прав/media | Auth и приватность | Проверка инцидента без раскрытия PII; аудит |
| Возраст backup/результат restore drill | Готовность к аварии | Восстановить процесс и повторить drill |

Пороги, SLO, каналы уведомлений, доступ к панели и ответственные не назначены. Телефон/адрес/order ID не используются как высококардинальные metric labels. Сигнал должен вести к runbook; список не означает существующий мониторинг.

## Условия готовности

При выборе Vercel/Supabase нужна отдельная оценка. Здесь нет provisioning/deploy, все ресурсы **unprovisioned**.
